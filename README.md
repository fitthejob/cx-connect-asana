# Asana Self-Service Contact Flow: Architecture Overview

---

## What this does

A caller reaches this module (invoked from connect-terraform's main inbound
flow), describes their issue out loud, and the call is recorded, transcribed,
and turned into an Asana task automatically; no agent involved. The caller
hears their case number read back before hanging up.

**End result:** an Asana task is created containing the case number, the
caller's ANI (phone number), and, once transcription finishes, the full
text transcript of what the caller said, all without any agent involvement.

---

## Call flow, in order

1. Caller enters the module. Flow logging is enabled for visibility.
2. A prompt asks the caller to describe their issue.
3. A beep plays (S3-hosted audio) to cue the caller that recording is about
   to start.
4. Call recording is enabled (IVR audio only, no agent/customer analytics).
5. A dedicated Lex bot listens and holds the line open until the caller
   stops talking (dynamic silence detection, capped at 30 seconds). This
   replaces an earlier static 20-second pause.
6. Recording is disabled.
7. A Lambda creates the Asana task and returns a case number.
8. The case number is read back to the caller (spelled out character by
   character via SSML), then the call disconnects.

---

## High-level components

- **Contact flow module** (`modules/asana-flow-module`): the Connect
  resource itself. Its JSON is generated by `scripts/asana-integration-flow.ts`
  using `connect-flow-builder`, not hand-authored.
- **Lambda: asana-ticket:** invoked mid-flow to create the Asana task and
  return a case number back into the flow.
- **Lambda: recording-transcribe:** triggered after the call recording
  lands in S3; transcribes it via Amazon Transcribe.
- **Lambda: asana-transcript-update:** takes the finished transcript and
  appends it as a comment/note on the Asana task.
- **DynamoDB (contact-correlation table):** links a Connect contact ID to
  its Asana task GID so the transcript Lambda can find the right task later.
- **Dedicated Lex V2 bot** (`modules/lex-speech-detection`): a minimal,
  single-intent bot whose only job is detecting when the caller stops
  talking. It does not make routing decisions; every possible outcome
  (intent match, no match, timeout, error) leads to the same next step.
  It is kept separate from connect-terraform's shared menu-routing bot so
  this module's deploys aren't coupled to that bot's release cycle, and so
  a caller's free-form issue description can't accidentally trigger an
  unrelated menu intent.
- **S3:** hosts the beep prompt audio and stores call recordings.
- **Secrets Manager:** holds the Asana API token used by the Lambdas.

---

## What appears in Asana

A single task is created per call, in the project configured for the
deployment. It goes through two states:

**When the call ends** (task created immediately, before transcription):

- **Task name:** `Self-service ticket: <customer ID or contact ID>`
- **Notes:** `Transcription pending...`, followed by the Customer ID and
  Caller ANI, if available

**Once transcription finishes** (notes are replaced, not appended to):

- **Notes:** the full call transcript, followed by the Customer ID and
  Caller ANI, if available

The case number read back to the caller on the call is the task's Asana
GID, so the caller's case number and the Asana task are the same
identifier.

## API surfaces

**Asana API** (`https://app.asana.com/api/1.0`):

- `POST /tasks`: called by the asana-ticket Lambda when the call ends, to
  create the task and get back its GID (used as the case number).
- `PUT /tasks/{gid}`: called by the asana-transcript-update Lambda once
  transcription completes, to replace the task's notes with the final
  transcript.

**AWS Secrets Manager:**

- `GetSecretValue`: called by both Asana-facing Lambdas to fetch the Asana
  API token at invocation time, rather than storing it in an environment
  variable.

**AWS Transcribe:**

- `StartTranscriptionJob`: called by the recording-transcribe Lambda once
  a call recording lands in S3, pointing Transcribe at the recording and
  at an S3 output location for the finished transcript. This is a
  fire-and-forget call; Transcribe runs the job and completion is picked
  up separately via EventBridge.

**AWS DynamoDB** (contact-correlation table):

- `PutItem`: called by the asana-ticket Lambda to record the mapping from
  a Connect contact ID to its new Asana task GID.
- `GetItem`: called by both the recording-transcribe Lambda (to look up
  the Asana task GID for tagging the transcription job) and the
  asana-transcript-update Lambda (to look up the Asana task GID, customer
  ID, and caller ANI for the final notes update).

**AWS S3:**

- `GetObject`: called by the asana-transcript-update Lambda to read the
  finished transcript JSON that Transcribe wrote out.

**Amazon Connect flow actions** (consumed by this module, not called by
Lambda code):

- `InvokeLambdaFunction`: invokes the asana-ticket Lambda mid-flow.
- `UpdateContactRecordingAndAnalyticsBehavior`: toggles call recording on
  and off around the caller's description.
- `ConnectParticipantWithLexBot`: hands the call to the dedicated Lex bot
  for speech-end detection.

## Key architectural decisions

- **Flow JSON is generated from code, not hand-authored in Flow Designer:**
  a TypeScript generator (`scripts/asana-integration-flow.ts`) builds the
  flow with `connect-flow-builder` and writes out the JSON that Terraform
  loads via `file(...)`. This mirrors connect-terraform's own pattern for
  its main inbound flow, keeps the flow reviewable and diffable in git, and
  lets the flow be regenerated automatically in CI with live values (Lambda
  ARNs, bot alias ARN) baked in at deploy time instead of hand-wired.
- **Speech-end detection uses a dedicated, minimal Lex bot instead of a
  fixed wait duration:** recording used to stop after a static 20-second
  pause regardless of how long the caller actually spoke. A single-intent
  Lex bot now listens for natural silence instead, so short answers finish
  quickly and longer ones aren't cut off; a 30-second cap still bounds the
  worst case. The bot exists purely to detect when speech has ended; every
  outcome routes to the same next step, so it never makes a routing
  decision.
- **Recording, transcription, and the Asana update are decoupled into
  separate Lambdas connected by S3 and DynamoDB, not one synchronous
  chain:** the flow only needs to create the case and read back a number
  while the caller is still on the line. It doesn't wait for transcription,
  which can take longer than a caller should be on hold. Transcription and
  the Asana note update instead run asynchronously off the recording
  landing in S3, using the DynamoDB correlation table to find the right
  Asana task afterward.
- **This repo owns only the Asana module, not the Connect instance or main
  inbound flow:** those are connect-terraform's responsibility. Keeping
  this feature in its own repo, deployed as a contact flow module with its
  own Terraform state, means it can be built, tested, and deployed
  independently, and connect-terraform only needs to reference it by ID.

## Notable problems solved

- **Recording silently failed to enable, with zero error anywhere:** the
  recording action supports an optional analytics configuration
  (`VoiceAnalyticsBehavior`), but that setting is only valid when both the
  agent and customer legs are being recorded. This module only records the
  IVR leg (no agent yet at this point in the call), so analytics can't be
  turned on. Nothing surfaced that as an error; the action just failed at
  runtime with no message in flow logs, CloudTrail, or the CLI. Root cause
  was found by reading the raw API documentation for the action directly.
  Fix: don't request analytics behavior on IVR-only recording.
- **A Lambda invoked from the flow was silently unreachable:** IAM
  permissions and the Lambda's own resource policy both looked correct, but
  Connect still couldn't invoke it. Connect requires a separate,
  instance-level association before any flow can call a given Lambda at
  all; this is unrelated to IAM. Fix: add that association as its own
  Terraform resource.
- **A prompt audio file in S3 failed to play, also with no visible error:**
  Connect fetching a prompt from S3 requires an explicit bucket policy
  statement granting the Connect service principal read access, scoped to
  the specific Connect instance. This is separate from any IAM role
  permission. Fix: add that bucket policy statement.
- **No reliable way to know when a caller had finished speaking:** a fixed
  wait time either cut callers off early or made short calls wait
  needlessly long. Solved by introducing a minimal, purpose-built Lex bot
  used only for silence detection (see architectural decisions above),
  tuned via Lex's own timeout session attributes rather than a static
  delay.
- **No way to test a contact flow module on its own:** Amazon Connect can
  only run a module from inside a real flow, not standalone. Solved with a
  disposable wrapper flow, generated the same way the main module is, that
  just invokes the module and disconnects; it's pushed to a shared test
  contact flow for live testing without touching the real inbound flow.

## How it fits with connect-terraform

This repo owns only the Asana module and its supporting Lambdas and data.
It does not own the Connect instance, the main inbound flow, or the
queues; those live in `connect-terraform`. Once deployed, the module gets
invoked from connect-terraform's main inbound flow the same way its other
flow modules are (e.g. `CUSTOMER_LOOKUP_MODULE_ID`), via an ID threaded
through CI, not through cross-repo Terraform state.

## Planned future features

- **Associate the case to a customer record:** resolve the caller's ANI to
  a known customer profile (e.g. via Amazon Connect Customer Profiles) and
  attach that identity to the Asana task, instead of just recording the raw
  phone number.
- **Dynamically create Amazon Connect Cases:** Connect has its own native
  case-management service (Amazon Connect Cases, separate from Asana) with
  a `CreateCase` API, callable from a Lambda the same way the Asana Lambda
  is called today. This has been confirmed possible; it requires a
  customer profile ARN (from Customer Profiles) and a title, so it depends
  on the first item above. Worth exploring as either a replacement for or
  companion to the Asana ticket, once customer-profile lookup exists.

## Scaling considerations

**Current behavior:** the recording-transcribe Lambda is invoked directly
by an S3 `ObjectCreated` event notification when a call recording lands in
the bucket. There is no queue between S3 and the Lambda. Amazon Transcribe
itself already runs each transcription job asynchronously in the
background once started, so the Lambda's own job is brief: start the job
and return.

**At enterprise scale**, direct S3-to-Lambda invocation has no backpressure.
A burst of calls ending at once, for example after an outage or during
peak volume, fires that many concurrent Lambda invocations simultaneously,
with no smoothing. The concern isn't the transcription work itself
(Transcribe already scales that independently); it's:

- **Lambda concurrency.** A large burst can hit account or function
  concurrency limits, causing throttling and retry storms instead of
  graceful buffering.
- **Retry and failure handling.** S3's built-in retry behavior for async
  Lambda invocations is blunter than a proper queue's visibility timeout
  and dead-letter queue, which give controlled retries and a durable place
  to inspect failures.
- **Transcribe's own concurrent-job quota.** `StartTranscriptionJob` has an
  account-level limit on concurrent jobs. A sudden spike could get
  throttled by Transcribe even if the Lambda invocations themselves
  succeed.

The standard fix at that point is inserting an SQS queue between S3 and the
Lambda (S3 to SQS to Lambda), with a controlled batch size and Lambda
concurrency, to smooth bursts into a steady rate rather than one burst of
simultaneous invocations. This isn't needed at current volume, but is the
natural next step if call volume grows significantly.

## Validation and testing

Every deploy pushes the generated flow JSON to a permanent
"Validation-Sandbox-Module-Asana" resource first and validates it against
the live Connect API before applying it to the real module. This surfaces
schema errors immediately instead of after a broken production deploy.
Manual end-to-end testing (since Connect has no way to invoke a module
standalone) uses a disposable wrapper flow that simply invokes this module
and disconnects, pushed to a shared test contact flow with a real phone
number pointed at it.
